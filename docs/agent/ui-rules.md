# UI 设计规范

修改 JSX、组件、布局、主题或样式前，必须先阅读本文件。

## 浏览器验收门槛

任何 UI 功能都必须在 `feature_list.json` 标记 `"ui": true`。完成前必须：

1. 从导航前开始监听浏览器 `console.error` 和未捕获页面异常。
2. 使用 `domcontentloaded` 打开每个受影响路由，短暂等待，并实际执行改动涉及的交互。
3. 发现错误时保持 `in_progress`，修复后重新执行完整浏览器检查。
4. 在功能条目写入 `browser_verification`，包含 `routes`、`interactions`、空的 `console_errors`、空的 `page_errors` 和 `checked_at`。
5. 运行 `npm run verify:harness`；只有通过后才能将状态改为 `passing`。

构建成功、页面截图或“已打开页面”的文字说明都不能替代控制台与页面异常检查。

## 组件复用优先

- 编写 UI 前，先检查 `src/components/ui/` 中是否已有合适的 shadcn 组件。
- 如没有可直接使用的组件或需要通过拼装已有组件实现的组件，创建新的业务组件并做到最大化的抽象，确保该组件在后面的项目中可以通过传参复用。
- 已有基础组件时，必须通过其正式 API 和 variant 使用，不能用带样式的 `div` 重新实现。
- 不得为了处理单个页面的特殊情况而修改基础组件的全局默认行为。

## 设计系统分层

设计系统分为以下四层。需要调整设计时，应修改能够覆盖需求的最高层级，不要在下层重复覆盖。

1. `src/styles.css`：全局 Design Token，包括颜色、圆角、字体、主题和通用动效。
2. `src/components/ui/`：shadcn 基础组件，包括 variant、尺寸、交互状态和无障碍行为。
3. `src/components/features/app-layout.tsx` 及现有页面 Shell：负责视口、导航、内容宽度、滚动区域和页面骨架。
4. `src/components/features/`：负责业务组件组合和具体任务流程。

修改位置按以下规则判断：

- 所有页面都应变化：修改 `src/styles.css` 中的全局 Token。
- 某类组件的所有实例都应变化：修改对应 shadcn 基础组件或共享 variant。
- 所有登录后页面都应变化：修改 `AppLayout` 或对应的现有 Shell。
- 只有当前页面存在特殊需求：才允许使用页面级样式。


## 全局 Design Token

### 颜色

- 使用 `src/styles.css` 已定义的语义变量：`background`、`foreground`、`card`、`popover`、`primary`、`secondary`、`muted`、`accent`、`destructive`、`border`、`input`、`ring`，以及图表和侧边栏颜色。
- 浅色主题定义在 `:root`，对应的深色主题定义在 `.dark`。

以下情况可以例外：

- 支付宝、微信等第三方品牌的官方颜色，且品牌识别本身属于控件功能的一部分。
- 标准语义色板无法满足的数据可视化序列。

### 圆角、边框和阴影

- `src/styles.css` 中的 `--radius` 是唯一的基础圆角参数，现有 `radius-sm` 至 `radius-4xl` 均由它派生。
- 使用由全局 Token 驱动的标准 `rounded-*` 工具类，业务代码中禁止新增任意圆角值。
- 调整全局圆角时只修改 `--radius`，不要逐个修改组件。
- 边框用于划分结构，避免装饰性边框、粗彩色侧边框和多层嵌套边框。
- 阴影仅用于浮层或确实需要表达层级的位置。普通内容优先通过边框和背景层次区分。

### 字体与排版

- 产品界面统一使用 `src/styles.css` 中配置的 Geist Variable。未经明确的产品设计决策，不得引入新的 UI 字体。
- 后台界面使用紧凑、固定的字号层级，不使用适合营销页面的流式大标题。
- 使用现有字号和字重体系建立层级，不添加任意像素字号。
- 金额、流量、日期、时长和需要纵向比较的指标应使用 `tabular-nums`，避免数字宽度变化造成跳动。
- 长段正文每行宜控制在约 65–75 个字符；表格和数据区域可以更宽。

### 间距与尺寸

- 使用 Tailwind 标准间距体系。除外部资源或经过测量的集成限制外，不使用任意像素值。
- 优先在父级布局中使用 `gap`，不要给每个子元素重复添加 margin。
- 能通过 `min-*`、`max-*`、内容固有尺寸、Flex 或 Grid 表达时，不设置固定宽高。
- 多个页面共用的 Shell 尺寸应定义在 `AppLayout` 或共享 Token 中，不能分散到各页面。

### 动效与层级

- Dialog、Popover、Tooltip、Dropdown 和 Toast 使用现有组件的 Portal。禁止使用 `z-[9999]` 一类任意层级解决遮挡问题。



## 页面布局体系

- 登录后的管理后台和用户中心路由必须使用现有 `AppLayout`，页面内部不得重新实现侧边栏、顶部栏、视口或内容滚动容器。
- 登录、注册和密码相关页面必须复用现有 `AuthLayout` 模式。
- 禁止嵌套多个页面 Shell。
- 页面只负责当前任务内容，不负责全局视口行为。


## 数据密集型界面

- 可比较的结构化记录统一使用现有 `Table` 和 `DataTable` 模式。
- 在小屏幕上，应通过横向滚动、列优先级或专用移动端条目保持可读性，不能持续压缩桌面表格直至内容被裁剪。
- 每行操作的位置和排列顺序必须保持一致。
- 数值列采用一致的对齐方式；需要比较时使用 `tabular-nums`。
- 必须明确设计加载、空数据、错误和正常数据四种状态。
- 空状态需要说明当前为什么没有内容，并在存在合理操作时给出明确入口。

## 表单与操作

- 表单使用现有 `Form`、`Field`、`Label`、`Input`、`Select`、`Checkbox` 等基础组件组合。
- Placeholder 只能提供示例或提示，不能代替字段 Label。
- 校验错误必须具体、靠近对应字段，并通过正确的无障碍属性与字段关联。
- 只有当用户能从当前表单状态理解原因时才禁用提交按钮，否则必须说明阻塞原因。
- 操作进行中必须防止重复提交，同时保留清楚的动作名称或进度提示。
- 按钮文案应说明动作及对象，例如“保存设置”“删除用户”，避免使用“确定”“是”等含义依赖上下文的词。
- 破坏性操作必须使用 destructive variant，并根据操作能否恢复提供相应程度的确认。

## 交互状态

每个交互组件都必须处理与其功能有关的状态：

- 默认、悬停、键盘聚焦、按下、禁用和加载状态。
- 适用时提供选中或展开状态。
- 适用时提供错误、警告、成功和信息反馈。

内容加载使用 Skeleton；短暂且不阻断任务的反馈使用 Sonner；需要持续展示的上下文消息使用 Alert；只有确实需要中断当前操作时才使用 Dialog 或 AlertDialog。新增 Modal 前，先考虑能否通过行内编辑或渐进式交互完成。

## 无障碍

- 满足 WCAG AA：普通文字对比度至少为 4.5:1，大号文字和有实际含义的界面图形至少为 3:1。
- 必须保留清晰可见的键盘焦点。除非提供等效方案，否则禁止移除 Focus Ring。
- 优先使用语义化 HTML，只有原生语义不足时才补充 ARIA。
- 只有图标的按钮必须提供无障碍名称，通常还应提供 Tooltip。
- 有信息含义的图片必须提供准确的 alt；纯装饰图片使用空 alt。
- 关键内容和操作不能只在 Hover 时出现。
- 移动端主要触控操作的目标区域应至少达到 44×44 CSS 像素。桌面端紧凑控件也必须支持键盘操作。
- 支持减少动态效果偏好和浏览器缩放，缩放后不能丢失内容或操作入口。

## 图标、文案与格式化

- 新增通用 UI 图标优先使用 Lucide。只有缺少品牌或业务专属图标时才使用其他图标库。
- 同一组控件中的图标尺寸和线条风格必须一致。
- 界面文案应简洁、准确并指向具体操作。
- 同一个业务对象始终使用同一个名称，不为追求措辞变化而混用近义词。
- 日期、货币、流量和时长必须使用现有共享格式化函数，不在页面中临时拼接。
- 错误信息应说明失败原因和用户可以采取的下一步，同时避免暴露密钥或内部实现细节。
