# 订单、收款与发放

## 模块边界

- `commerce/orders.js`：纯订单领域。创建商品快照、校验订单有效性、关闭订单；不导入支付、钱包、渠道或发放模块。
- `commerce/settlement.js`：余额预占、释放与以分为单位的收款金额分配。
- `commerce/gateway.js`：渠道协议、签名请求、创建交易与查单；不读取业务订单或操作套餐。
- `commerce/payments.js`：支付方式校验、独立渠道交易记录、支付重试、人工收款凭据。
- `commerce/checkout-workflow.js`：应用编排。组合订单保存、余额预占、收款确认与已有交付适配器。各领域服务不互相调用。
- `server.js`：鉴权、报价适配器、持久化适配器、路由，以及既有账单/VIP/返利/3x-ui 交付链路。新领域模块不依赖 HTTP 请求或 server 全局变量。

前端由 `order-summary.tsx` 展示快照、`online-payment.tsx` 处理线上付款，`cashier.tsx` 组合状态展示和操作。提交订单页不选择或调用线上付款平台。

收银台独立路由为 `/cashier/:id`，使用 `cashier-page.tsx` 自己的页面 Shell，不挂载用户中心布局。新订单提交直接跳转收银台；原 `/account/orders/:id` 和付款结果页对新版订单兼容跳转。订单读取继续通过受保护的 API 校验归属。Vite 的短链接代理限定为 `/c` 或 `/c/…`，避免误代理 `/cashier`。

## 接口

| 接口 | 职责 |
| --- | --- |
| `POST /api/orders/quote` | 获取商品、优惠及余额抵扣报价 |
| `POST /api/orders` | 保存待付款订单与金额快照，不请求渠道、不发放 |
| `GET /api/orders/:id` | 查看本人订单；过期时关闭并释放预占 |
| `DELETE /api/orders/:id` | 取消本人有效待付款订单；已发起渠道交易时先核查，渠道故障仍允许关闭并保留后续到账核查能力 |
| `GET /api/payments/platforms` | 获取可展示的支付平台与付款方式 |
| `POST /api/payments/orders/:id/start` | 为已有订单发起渠道付款；余额/零元订单在此显式确认 |
| `POST /api/payments/orders/:id/refresh` | 主动核查渠道与发放结果 |
| `POST /api/admin/orders/:id/mark-paid` | 管理员确认人工收款，记录身份、时间及备注，再进入交付 |

已有 `/api/payments/orders` 创建入口是提交订单的兼容别名，也不再直接发起付款。旧订单保留原支付链接与旧回调处理；充值继续使用原入口。旧报价入口保留平台字段，新订单报价不返回平台字段。

## 持久化与恢复

现有 `paymentOrders` 集合作为兼容投影，供历史账单、销售统计和交付链路读取。新增订单带 `checkoutVersion: 2`。商品及成交金额在提交时冻结，支付失败不删除或重新报价该订单。

渠道交易保存在 `app_records` 的独立 `paymentAttempts` 集合，以商户交易编号为主键，关联业务订单 ID；`paymentSessions` 保存每个订单当前的交易引用。先持久化交易编号与当前引用再请求渠道。超时重试复用原编号；切换渠道或重建已失败的交易会保留旧交易，即使订单兼容投影尚未更新也能恢复当前交易。无需新增数据库表。

线上与人工收款均先保存已收款状态，再调用既有幂等交付链路。交付失败保留已收款状态与失败信息，管理员可重试。重复回调不重复发放；人工收款后或其他渠道收款后又收到有效成功回调时，后台记录重复收款编号供核查。关闭/过期后到账进入异常核查，不自动发放。

订单生命周期、渠道交易状态、交付状态分别处理。单次渠道失败仍是待付款订单；未发起渠道交易的订单查看和取消完全不需要渠道。收银台每 5 秒查询本地订单；用户主动检查状态才查渠道。

## 并发与验证

支付相关入口使用进程内队列和 PostgreSQL advisory lock 串行执行，进入操作前重新读取应用快照，避免同时提交、人工确认、回调和重试相互覆盖。渠道 HTTP 请求具有 15 秒超时。锁采用全局粒度是因为现有应用按集合保存快照；因此较慢的渠道/交付操作会让其他收款操作排队。若后续需要高吞吐，应先改为订单级事务存储，再缩小锁粒度。

`npm run test:payment` 包括独立领域测试及真实隔离 PostgreSQL、模拟支付渠道和模拟 3x-ui 的端到端测试。必须配置独立 `TEST_DATABASE_URL`；支付测试会清空测试库中的 `app_records`，不可使用生产库。完整验收运行 `npm run verify`，UI 另记录实际浏览器 console/page-error 证据。
